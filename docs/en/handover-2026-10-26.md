# Handover: Buscheck, BLE lab, and the 250-byte name test

[English](handover-2026-10-26.md) · [Deutsch](../de/handover-2026-10-26.md)

Date: 26 October 2026
Status: field app works, parser bug reproduced, radio path needs a BLE 5 advertiser

## 1. Purpose

The goal is to read PaderSprinter bus data without the original app, test the
module's Bluetooth surface, and measure whether a 250-byte invalid-UTF-8 name
crashes `bluetoothd`.

The first result is data. The second is a measured crash. Root is a later phase.

## 2. Target

- Bus modules with OUI `78:C4:0E` (H&D Wireless), name `ivi` or `ivc`.
- BlueZ 5.78 fingerprint via PnP ID `1d6b:0246:054e`.
- Protocol 18 advertisement, route text in GATT `0x201f/0x2020`.
- Action characteristic `0x1f1f/0x1f20`.
- The bus keeps driving if `bluetoothd` restarts. Only Bluetooth drops.

## 3. The bug

`name2utf8()` in `src/eir.c` copies a remote name into a 250-byte stack buffer.
The name field can be 254 bytes. Invalid UTF-8 takes the `strncpy()` path, so a
250-byte name writes to the end of the buffer and the following loop reads past
it. ASan reports a stack-buffer-overflow at `eir.c:139`.

- Minimum trigger: 250 name bytes.
- Payload: `fb 09` + 250 × `ff` (252 bytes).
- With the service UUID for app visibility: `02 01 06 03 03 1f 1f fb 09` + 250 × `ff` (259 bytes).
- Upstream fix: clamp `len` to `HCI_MAX_NAME_LENGTH`, commit `381b5d0`.

## 5. Hardware findings

- PC adapter: ASUS USB-BT500, BLE 5, accepts 252 and 259 bytes over raw HCI.
- `btmgmt add-adv` only supports 31 bytes. Use `hci_adv.py` for extended data.
- One controller does not report its own advertisements. The PC cannot parse
  what it advertises itself.
- Pi onboard adapter: BLE 4.2, 31 bytes, no extended advertising.
- Pi + ASUS on kernel 5.15: raw HCI extended commands work, `btmgmt` still says 31.
- ESP32 WROOM: BLE 4.2, not enough.
- ESP32-S3: BLE 5, extended advertising, suitable for a backpack advertiser.
- Phone: BLE 5, but Android sends service data, not a raw name.

## 6. What works

- Parser harness: ASan crash at 250 and 253 bytes, clean after the clamp.
- PC raw HCI advertiser: 252 and 259 bytes accepted.
- Pi raw HCI advertiser: 252 and 259 bytes accepted on the ASUS.
- Pi virtual bus: BlueZ 5.78 GATT server, legacy bus advertisement, `/crash`
  removes and restores the advertisement.
- Phone app: scan, decode, route read, GATT inventory, actions, SDP, RFCOMM,
  BAP/BASS, crash watchdog, 250 ms presence measurement.

## 7. What does not work

- PC self-test: the same controller does not see its own advertisement.
- Phone app EIR probe: sends service data, not a name.
- Pi onboard extended advertising: BLE 4.2.
- ESP32 WROOM extended advertising: BLE 4.2.

- A crash is inferred from advertising silence, not a device log.
- The app's EIR probe is not the trigger. The Pi or S3 is.

- A negative field result is not a non-vulnerability proof.

### Build and flash commands

ESP-IDF v5.4.3 was installed for this build at
`/tmp/buscheck-esp-idf-v5.4.3`, commit

```sh

```

Flash port: **not established for an S3**. `/dev/ttyUSB0` identified the original
ESP32 through a CH340 bridge. No `/dev/ttyACM0` S3 was available.
After connecting the correct board, verify its chip and flash size, then use its
actual port:

```sh
python -m esptool --port /dev/ttyACM0 chip_id
python -m esptool --port /dev/ttyACM0 flash_id
idf.py -p /dev/ttyACM0 flash monitor
```

`/dev/ttyACM0` above is a placeholder, not a confirmed flash port. The firmware
uses the 8 MB flash setting and the larger single-app partition. The first build
compiled and linked but failed the default 1 MB partition size check. The larger
partition corrects that configuration issue.

### Implemented behavior

- One fixed, literal 259-byte extended advertising payload. Prefix:
  `02 01 06 03 03 1f 1f fb 09`, followed by exactly 250 `ff` bytes.
- One non-connectable, non-scannable advertising set, instance 0, 1M PHY.
- AP `janosch`, password `Jan0sch?!`, default DHCP at `192.168.4.1`.
- Embedded offline Buscheck page, Start and Stop, one-second status polling.
- `/start` and `/stop` support POST and GET. `/status` returns `running`,
  `sent`, and `error`. Status is also logged once per second on serial.
- Start and Stop wait for controller callbacks. The 700 ms callback timeout
  reports an error rather than claiming success. Late callbacks update status.
- `sent` counts controller-confirmed starts since boot, **not radio packets**.
  The page labels this value "Started sessions".
- Advertising remains off at boot. A normal software reboot requests Stop.
  Neither running state nor AP configuration is saved by this firmware.

  bytes (21%) free in the `0x177000` app partition. The successful build log

- Read-only firmware review: no concrete actionable bugs reported.
- Pi SSH: reachable as `samy@ubuntu.local`. The specified BlueZ 5.78 daemon and
  virtual bus on `hci1`, port 8081, were already running and were left running.
- Pi baseline: `POST /crash` returned `{}`. A local HTTP status sample at

capture complete extended advertising reports, including fragment reassembly.
`hci1` is already the virtual bus advertiser. A second BLE 5 scanner avoids
depending on simultaneous scan and advertising support from that adapter.

## 16. Android Buscheck evidence capture

The `exploit/` debug app now records evidence for authorized lab tests. It does
not infer a vulnerability or a target crash from missing advertisements.
See [the capture guide](buscheck-evidence-capture.md) for the recording procedure
and the target-side evidence still required.

### Changes

- Raw candidate advertisements retain full SHA-256, bytes, Android scan metadata,
  scan timestamps, and callback receipt timestamps. Exact complete 259-byte
  reports are distinguished from service-data substitutes and incomplete data.
- A separate nominal 250 ms observer records scanner health and bus presence.
  The freshness window is 1,500 ms; this is not 250 ms outage accuracy.
  Scanner failures, delayed sampling, and queue loss invalidate measurements.
- The Capture page adds manual baseline/start/stop markers and file attachments.
  Markers do not transmit anything or confirm a transmission. Attachments retain
  original bytes and hashes, with a 16 MiB/file and 16-file/session limit.
- ZIP exports include `evidence-summary.json`, observations, markers, and attached
  files. Imports validate supplied event-log and attachment hashes. The 256 MiB
  decompressed import limit also counts unknown entries.
- Android name probes now report unsupported instead of presenting service data
  as an exact-name reproduction. Advertising gaps are no longer labelled crashes.

The mobile-design skill guided reuse of existing Material controls and semantic
colors. The technical-writing skill guided the separate capture procedure.
