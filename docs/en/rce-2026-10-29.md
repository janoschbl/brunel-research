# RCE work on the line 11 target

[English](rce-2026-10-29.md) · [Deutsch](../de/rce-2026-10-29.md)

Date: 29 October 2026
Target: `78:C4:0E:C0:2B:D7`, profile `p-8eef9540`, BlueZ 5.78
Status: exploit stages implemented, control-flow offsets still need a firmware dump

## Result

My evening capture does not support my earlier claim that the EIR name bug is a
return-address overwrite. On stock 5.78 the 253-byte name writes three bytes into
a six-byte alignment gap. The out-of-bounds loop then stops on the zero byte of
the saved length register. No saved register and no return address is
overwritten.

What remains is a denial of service on fortified or ASan builds, and a very small
stack read. A full RCE needs a second stage. The only remote write primitive on
this target is the vendor action characteristic `0x1f20`.

Here I record the corrected primitive, the action stage, the ROP builders, and
what is still missing.

## What the line 11 capture contains

The completed session has 31,485 events. The line 11 address contributes 7,473
scan reports between 18:16:41.816 and 18:33:29.144. 7,410 decode as line 11 and
63 carry protocol 18 without line text. RSSI is −94 to −46 dBm, median −57.

The same address returns name `BlueZ 5.78` and PnP bytes `026b1d46024e05`. The
service map contains `0x201f/0x2020` for route text and `0x1f1f/0x1f20` for
actions. Route reads succeed before the failed pairing attempt.

The route text is dynamic. It moves from `Langer Weg` through `Fröbelstraße`,
`Gierstor`, `Detmolder Tor`, `Maspernplatz`, `Neuhäuser Tor`, `Westerntor`, to
`Hauptbahnhof`. This is operational data, not a static name.

## The EIR primitive is smaller than reported

`name2utf8()` in `src/eir.c` copies `data_len` into `char utf8_name[250]`.
`data_len` can be 253. The copy overflows by three bytes. The buffer is not
terminated, so the following loop reads past it.

The stack layout defeats the obvious exploit. GCC 12 for ARMv7 with `-O2
-fomit-frame-pointer` places the buffer at `sp+4`, the first saved register at
`sp+260`, and the saved return address at `sp+276`. The copy ends at `sp+257`.
The first saved register is three bytes away.

The loop does not close the gap. The caller's saved `r4` is the AD type, `0x09`.
Its second byte is zero. The loop replaces byte 0 with a space and stops at byte
1. The saved return address is never touched.

The same layout appears with Clang, with a frame pointer, and at `-O0`. The
offsets differ, but the gap stays larger than four bytes.

My lab result on x86-64 with the exact 5.78 source:

```text
plain build:  name length=1, name 41
ASan build:   stack-buffer-overflow, WRITE of size 253, eir.c:136
FORTIFY build: *** buffer overflow detected ***, SIGABRT
```

A plain build survives. A fortified build aborts. That is the real impact.

## The action stage

`0x1f20` is writable and handled by the vendor app, not by BlueZ. The ATT layer
accepts up to 512 bytes per value. `check_length()` rejects larger values and
offsets above 512, so the prepare-write integer overflow cannot wrap.

A 512-byte value reaches the app in one of two ways:

1. Direct write request when the negotiated MTU is 517.
2. Prepare write at offset 0 with 509 bytes, prepare write at offset 509 with
   the remaining 3 bytes, then Execute Write.

My field capture shows MTU 517 negotiation succeeding. The app accepted no
one-byte action in that run, but Android rejected the submission before a remote
callback. The server-side permission is still unknown.

If the app copies the value into a fixed buffer, the value is the control-flow
stage. The exploit sends a cyclic pattern by default. With `--system` and
`--gadget` it sends a ret2libc chain for ARMv7, AArch64, or x86-64.

## Chain

```text
scan and fingerprint
  -> EIR name, 253 bytes, measure silence
  -> connect, discover 0x1f20
  -> prepare write 509 + 3, execute
  -> ROP: pop r0; command; system
```

The EIR stage is also the recovery test. A fortified target aborts and
`bluetoothd` restarts. The action stage waits for advertising to return before
it connects again.

## Running it

Dry run against the in-process mock:

```sh
cd research
.venv/bin/brunel rce --mock --dry-run
```

Field run with a pattern:

```sh
.venv/bin/brunel rce --transport usb:0 --scan-seconds 20
```

Field run with offsets from a firmware dump:

```sh
.venv/bin/brunel rce \
  --profile armv7 \
  --system 0x76e5a1c1 \
  --gadget 0x76e4b2f0 \
  --offset 264 \
  --cmd 'killall bluetoothd'
```

`--offsets 256,264,272` tries several offsets in one run. A crash is recorded
per offset. `--action-handle 0x0012` skips discovery.

The result is JSON. `--out` writes it to a file.

## What is still missing

- The vendor app binary. The offset, the `system` address, and the gadget are
  build specific.
- The action permission and the app's length handling. The field run only shows
  Android-side rejection.
- A target-side log or core dump. Advertising silence is still an inference.
- A check whether the app runs as root. A crash there is not a `bluetoothd`
  crash.

Without the binary the action stage is a crash probe, not a proven shell. The
code and the chain are complete; the addresses are not.

## Limits

- The EIR stage does not prove a crash on the bus. A plain build survives.
- The action stage can change passenger-visible state.
- One connection at a time. Passengers may contend.
- The mock is not BlueZ. It only checks the control flow of the exploit code.
- A negative action result is not a non-vulnerability proof.

## Update 2026-11-06: the action path was never exercised

The field runs reported `writeCharacteristic abgelehnt` for every action. That
was a local Android rejection, not a remote verdict. The app discarded the
numeric status and reused a cached service list after a disconnect. The
characteristic is `PROPERTY_WRITE`, so the API refuses a stale or busy client
with status 201 before any bytes leave the phone.

The client and the app now:

- log the integer status and the characteristic properties,
- reconnect and drop the cached services on 201,
- negotiate MTU 517 before an action write,
- use a write command (`0x52`) when the MTU fits the value,
- fall back to prepare write at `mtu - 5` and Execute Write,
- add a length ladder that stops at the first advertising gap.

The ladder is the missing offset oracle. The first crashing value length is the
distance to the first overwritten control word, or to a stack canary. A remote
run can measure it without a firmware dump.

Lab proof of the full path, with BlueZ 5.78 on two virtual controllers and a
256-byte handler:

```sh
lab/scripts/action-e2e.sh     # PWNED-GATT with command and prepare mode
lab/scripts/action-rop.sh     # x86-64 and ARMv7 chain proof
```

The ARM builder now keeps the command pointer even, uses an explicit
`system_thumb` mode, supports a three-register gadget (`pop {r0, r4, pc}`), and
can point at a fixed command address. The older chain set the Thumb bit on the
data pointer and read one byte into the string.

Still unknown for the real target: the offset, a canary, the libc base, a
gadget, and the process user. See
[the field run](rce-field-run-2026-11-07.md).
